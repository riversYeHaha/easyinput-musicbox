# 奇妙音乐盒开发经验总结

> EasyInput V2.0 开发板（ESP32-S3R8 + 8MB PSRAM + 16MB Flash）上的"AI 音乐盒"项目实战记录。
> 本文沉淀开发思路、里程碑拆解与全部踩坑记录，供后续维护与同类项目参考。

---

## 一、项目一句话

板载 8 个按键 + 旋钮 + WS2812 灯环：按键触发录音/AI 生成音乐，歌曲存 Flash 离线播放；AI 生成由电脑端网页（Vite + Web Serial）通过 USB CDC 对接阶跃星辰 API 完成，生成结果再分块写回开发板。

```
┌─────────────┐   USB CDC (JSON行 + 二进制帧)   ┌──────────────┐   HTTPS   ┌────────────┐
│  ESP32-S3   │ ◄────────────────────────────► │  网页控制台   │ ────────► │ 阶跃星辰API │
│  音乐盒固件  │        停等ACK+CRC32           │ (Web Serial) │           │ 音乐/ASR    │
└─────────────┘                                 └──────────────┘           └────────────┘
```

**核心约束**：ESP32 只负责录音、存储、播放、灯效；一切重计算（AI 生成、ASR）都在电脑端网页完成，板上 Flash 只落最终 MP3。

## 二、开发思路

### 1. 为什么按里程碑（M1~M6）纵向切片

每个里程碑都是**端到端可验证的最小闭环**，而不是按"先写完全部驱动再写业务"横向分层：

| 里程碑 | 内容 | 验证标准 |
|---|---|---|
| M1 | 骨架：电源、按键、旋钮、灯、USB 协议、REPL | 按键有日志、灯能动、串口能对话 |
| M2 | 音频：I2S 录音 + Helix MP3 解码播放 + 4 槽歌曲库 | 能录能放 |
| M3 | 写板协议：网页 → 板的二进制分块传输 | MP3 从网页写进 Flash 并能播 |
| M4 | 录音上传 + S5 哼歌成曲 / S6 录音转文字 | 板 → 网页方向传输打通 |
| M5 | Wi-Fi 热点：手机连板子直接下载歌曲 | 浏览器访问 192.168.4.1 能下歌 |
| M6 | 全功能实板联调验收 | — |

好处在 M3 暴露得淋漓尽致：传输协议这种跨端功能，只有真把 4KB 二进制帧打过去才知道会丢字节。如果等到"全部写完再联调"，这些坑会全部堆到最后爆发。

### 2. 关键设计决策

- **协议双模**：同一根 USB CDC 上跑两种流量——JSON 文本行（命令/事件）和二进制帧（`0xAA55 | seq | len | payload | crc32`）。约定 `{` 开头的是文本行，`0xAA 0x55` 开头的是帧，字节级状态机双模解析。板↔网页两个方向复用完全相同的帧结构，CRC32 实现两端互验（测试向量 `crc32("123456789")=CBF43926`）。
- **停等 ACK + NACK 自愈**：单块 4KB，发一块等一块 ACK；CRC 错板端回 NACK，网页延迟 50ms 重发，同块 3 次才中止。低速链路（UART 115200）上停等足够，简单可靠远比窗口化重要。
- **Flash 三段式原子写**：先擦槽位 → 再写音频数据 → 最后写元数据头。头部带有效标记，中途断电只产生"无头数据"，开机扫描时自动作废，不会出现半首坏歌被播出来。
- **4 槽循环覆盖**：优先空槽，满了覆盖最旧。12.9MB 分区 ÷ 4 ≈ 每槽 3.3MB，对应 MP3 约 2~3 分钟。
- **灯效状态机集中管理**：录音红 / 生成跑马灯 / 完成绿闪3次 / 播放迪斯科随机色，所有模块只调 `led_status_set_mode()`，互不抢灯（写块期间录音红灯优先）。
- **Provider 可插拔**：网页端统一 `generate()` 接口，阶跃星辰只是第一个实现，后续可换服务商。

## 三、踩坑全记录（按时间顺序）

### 坑 1：Python 环境不一致导致构建神秘失败

**现象**：IDE 里能编译，命令行 `idf.py build` 报包缺失；或反之。

**根因**：IDE 用的是 `~/.espressif/tools/python/v5.5.5/venv`，而命令行 `export.sh` 默认激活 `python_env/idf5.5_py3.9_env`，两套环境的 pip 包不一致。

**修复/规约**：编译命令固定为 **先 source export.sh，后 source venv**（顺序不能反）：

```bash
source ~/.espressif/v5.5.5/esp-idf/export.sh
source ～/.espressif/tools/python/v5.5.5/venv/bin/activate
idf.py build
```

`idf.py fullclean` 后也必须用 venv 重建。

---

### 坑 2：M3 写板首块 CRC 必败——64 字节硬件 FIFO 溢出

**现象**：网页发来的第一帧永远 CRC 不匹配，后面的块反而有机会成功。

**根因**：固件**没有安装 USB Serial/JTAG 驱动**，走的是无驱动裸读路径——直接读 64 字节硬件 FIFO。4KB 帧高速涌入时 FIFO 溢出丢字节，CRC 自然对不上。首块必败是因为突发流量在会话开始时最猛。

**修复**：`usb_serial_jtag_driver_install()` 安装驱动，**RX 环形缓冲配 8192 字节**（≥ 一整帧 4106B + 余量），并 `usb_serial_jtag_vfs_use_driver()` 把 console 切到驱动路径。

> 教训：ESP32-S3 的 USB Serial/JTAG 不装驱动也能"看起来能用"（短文本没问题），但二进制大流量必死。凡是要传二进制，驱动 + 大环形缓冲是前置条件。

---

### 坑 3：驱动装好了 CRC 还是错——LIBC 偷偷改写 0x0D

**现象**：装了驱动后 CRC 仍偶发失败，且失败帧里总能发现 0x0D 字节对不上。

**根因**：ESP-IDF 默认 `CONFIG_LIBC_STDIN_LINE_ENDING_CR=y`，VFS 终端层会把输入里的 **0x0D（\r）改写成 0x0A（\n）**——对文本输入是贴心功能，对二进制音频是灾难。

**修复**：绕过 VFS 终端层，直接调底层驱动接口裸读：

```c
usb_serial_jtag_read_bytes(buf, sizeof(buf), 0);  // 非阻塞，无行尾转换
```

> 教训：**二进制传输必须全程走驱动 API，不能碰 stdio/VFS**。getchar/fread 这类看似无害的调用背后都可能有文本语义。

---

### 坑 4：NACK 发不出去——阻塞 getchar 卡死接收任务

**现象**：板端检测到 CRC 错误后，网页永远收不到 NACK，只能等超时重传，重传帧还被"吞掉"。

**根因**：`rx_drain_input()`（清空残留输入字节的函数）用**阻塞式 `getchar()`**，且调用顺序在发 NACK **之前**。缓冲区空时 getchar 永久阻塞 → 接收任务卡死 → NACK 躺在队列里发不出 → 网页重发的帧到达时任务已死，帧被残留逻辑错位消耗。

**修复**：

1. 排空改用非阻塞 `usb_serial_jtag_read_bytes(buf, 128, 0)` 读到返回 0 为止；
2. **顺序反过来：先发 NACK，再排空**。

> 教训：协议状态机里任何"清理现场"的动作都必须非阻塞；发送响应永远优先于清理输入。

---

### 坑 5：S4 回放报 speaker busy——暂停态漏判

**现象**：音乐暂停后按 S3 录音，录完按 S4 回放，日志提示喇叭忙，回放被中止。

**根因**：`player_is_playing()` 只对 `PL_PLAYING` 返回 true，**暂停态 `PL_PAUSED` 漏网**。录音前检查"喇叭是否空闲"时，暂停中的播放任务被判为空闲、没被终止，随后真正抢占喇叭时冲突。

**修复**：录音/回放入口不再判断状态，**直接调幂等的 `player_stop()`**——它能正确终止包括暂停在内的一切非空闲播放任务。

> 教训：状态机查询函数（is_xxx）的语义覆盖面容易随状态增加而腐化；**幂等的终止/复位操作比状态判断更可靠**。

---

### 坑 6：Wi-Fi 热点网页 404——httpd 通配符路由不生效

**现象**：手机连上热点，访问 `http://192.168.4.1/` 返回 404。

**根因**：ESP-IDF v5.5.5 的 httpd **默认用 `httpd_uri_match_simple`（strncmp 精确匹配）**，注册的 `/*`、`/song/*` 通配符路由被当成字面量，永远匹配不上 `/`。

**修复**：httpd 配置里显式指定：

```c
hcfg.uri_match_fn = httpd_uri_match_wildcard;
```

> 教训：ESP-IDF httpd 的通配符语义**不是默认开启**的，用 `*` 路由必须显式设置匹配函数。

---

### 坑 7：手机一连热点设备就重启——httpd 任务栈溢出

**现象**：开热点后手机一访问列表页，设备立即重启，串口无明确报错。

**根因**：两个叠加问题：

1. httpd 任务默认栈只有 **4096 字节**；
2. 请求处理函数里声明了 `uint8_t chunk[8192]`（下载分块）和 `char body[2048]`（列表页 HTML）——**栈上直接爆了**。

**修复**：

- 大缓冲区全部改 `malloc`/`free` 堆分配；
- httpd `stack_size` 从 4096 提到 **6144**（经验下限，处理大文件请求建议 ≥6144）。

> 教训：ESP32 栈溢出经常表现为"无预警重启"，串口可能什么都来不及打印。**凡在 httpd/回调任务里用超过 1KB 的缓冲区，一律上堆**。另外 DNS 绑定建议加 `SO_REUSEADDR` 并打 errno 日志，方便定位 53 端口占用。

---

### 坑 8：歌曲标题乱码——UTF-8 被拦腰截断

**现象**：中文歌名在板端显示为乱码或末尾一个"�"。

**根因**：槽头给标题留 48 字节，直接 `strncpy` 硬截，多字节 UTF-8 字符被从中间切断。

**修复**：写 `utf8_prefix_len()` 安全截断函数——从目标长度往前回退到合法 UTF-8 字符边界再截。**写入侧和加载侧都用**（加载侧兼容旧固件已写入的截断标题，重启后旧歌名也能正常显示）。

---

### 坑 9：S5 拉录音超时——`usb_serial_jtag_write_bytes` 的静默拒绝

**现象**：`rec_pull` 发出 `rec_meta` 后，网页帧解析卡在第一帧 payload 第 118 字节，之后完全静默，60 秒超时。板端无任何错误日志。

**根因**（最隐蔽的一个坑，值得细说）：

`usb_serial_jtag_write_bytes(buf, size, ticks)` 内部调 `xRingbufferSend(tx_ring_buf, buf, size, ticks)`。对 `RINGBUF_TYPE_BYTEBUF` 类型，FreeRTOS 的 `xRingbufferSend` 开头有这个检查：

```c
if (xItemSize > pxRingbuffer->xMaxItemSize) {
    return pdFALSE;   // Data will never ever fit in the queue.
}
```

`xMaxItemSize` 就等于创建时的 `tx_buffer_size`。**也就是说：单次写入 size > TX 环形缓冲时，立即返回 0——不等待、不写入、不报错**，跟超时返回 0 完全无法区分。

我们的配置：TX 缓冲 512 字节，而一帧 payload 4096 字节 → 第一帧 payload 写入立即失败，上层 `usj_write_all` 重试 5 次后放弃。而那 118 字节是帧头 + 部分小写入侥幸通过的部分。

**修复**（双保险）：

1. `CDC_TX_BUF_SIZE` 从 512 提到 **8192**（≥ 一整帧）；
2. `usj_write_all` 内部分块，**单次写入永远 ≤ `CDC_TX_BUF_SIZE`**——即使将来有人调小缓冲也不会复发。

修复后 420KB 录音分 103 帧完整回传，CRC 一次通过。

> 教训：**"返回 0 = 超时"是错误的心智模型**。凡是底层 API 返回短写/0 值，先把"请求本身非法（如超限）"和"暂时不可用"两种情况分开查。读驱动源码比猜快。

---

### 坑 10：哼歌成曲轮询 360 秒全是 PENDING——平台排队，不是代码问题

**现象**：S5 提交 `vocal_to_music` 任务成功，但轮询 73 次 × 5 秒全是 `PENDING`，直到超时。

**排查**：对照官方文档确认——参数/音频格式问题会走 `FAILED` 终态（`audio_transcode`、`no_speech_detected`），`PENDING` 纯表示"已入队未调度"。`stepaudio-3-music-preview` 是**限时免费 preview 模型**，`vocal_to_music` 又是最重的任务类型，长时间不出队是平台容量问题。

**修复**（客户端能做的）：

- 轮询超时 360s → 600s；
- 日志去抖：只在状态变化时打印（不再每 5 秒刷屏 PENDING）；
- 首次查询打印完整响应（看平台有没有返回队列位置等额外字段）；
- PENDING 超 90s 提示"排队中，可等可重试"；
- 超时报错里附带鉴别方法：按 S1 验证 `text_to_music` 能否出歌——能则是 vocal_to_music 路径繁忙，不能则是平台整体拥堵。

> 教训：异步任务 API 要把 **PENDING（排队）和 RUNNING（执行）分开对待**；超时文案里给出用户可操作的下一步，比一句"超时"有用得多。

## 四、可复用的方法论

1. **端到端纵向切片开发**：跨端协议类功能尽早打通真实链路，坑暴露在早期。
2. **二进制传输三铁律**（ESP32 USB Serial/JTAG）：
   - 必装驱动 + RX 环形缓冲 ≥ 最大帧；
   - 绕开 VFS/stdio，用驱动裸读（防行尾转换）；
   - 单次写入 ≤ TX 环形缓冲（防 xRingbufferSend 静默拒绝）。
3. **协议状态机里禁止阻塞调用**；响应优先于清理。
4. **幂等操作优于状态查询**（stop 优于 is_playing 判断）。
5. **嵌入式任务里大缓冲区一律上堆**；栈溢出 = 无预警重启。
6. **跨端 CRC 用已知测试向量互验**（`"123456789" → CBF43926`），先证明两端实现一致再怀疑传输。
7. **诊断信息设计**：失败日志带上状态机内部状态（如"帧解析 st=3 已收 118B"），让远端问题可定位。这次 rec_pull 就是靠网页端的解析器状态输出锁定的方向。
8. **默认值不信任**：ESP-IDF 的 httpd 匹配器、栈大小、LIBC 行尾处理，默认值都对文本友好、对二进制/大流量不友好。踩过的默认值都进了项目记忆，同类项目开工前先过一遍。
